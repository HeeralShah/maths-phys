# Google Gemini agent architecture comparison

**Research date:** 2026-11-01  
**Scope:** Current official Google documentation only. No model calls, SDK trial, paid requests, or benchmark were run. Pricing below is a calculated envelope from published list prices, not an observed cost.

## Recommendation

Use a custom Google ADK application deployed to Gemini Enterprise Agent Platform Agent Runtime as the managed production agent (option C). A hybrid of ADK orchestration plus direct Gemini Interactions API calls/tools (option B) is useful and likely necessary at the model-call layer, but option A's saved Antigravity agent should not be the system architecture. Keep source PDFs as explicit native document inputs to a complete-chapter ingestion stage; use structured outputs to make a source block/anchor model; then run bounded annotation and literature stages; validate the complete edition locally before publishing it. Put durable study state and chapter artifacts in the app's own store. Use File Search for a persistent searchable corpus, with locally owned provenance metadata and explicit cleanup rules.

ADK is the best fit because it makes our application own the workflow graph, tools, skills, model selection, session integration, and publication gate. It can orchestrate sequential and parallel agents/workflows, and ADK exposes Google Cloud deployment support. Native Gemini PDF understanding and JSON-schema outputs can be called as discrete steps from that application. Agent Runtime then hosts the ADK application and supplies managed execution, sessions/memory integrations, and Cloud controls. This hybrid is an architectural combination, not a dependency on the saved Antigravity agent.

No Google product supplies a full Google Scholar research workflow by itself. Google Search grounding provides web discovery and citations, not a structured scholarly citation graph or reliable paper relationship evidence. Keep a separate bibliographic source/provider and require evidence review for inferred links.

## The naming trap

“Managed agent” is overloaded in Google's current documentation:

1. **Gemini API managed agents / saved Custom Agents (A)** are configurations extending the **Antigravity agent**. The custom agent documentation explicitly says this and requires `base_agent: "antigravity-preview-09-2026"`. The named resource saves its instructions, tools, and environment files and is invoked through the Gemini Interactions API. It is not a blank user-owned agent runtime and it is not the Agent Development Kit.
2. **Agent Runtime / Gemini Enterprise Agent Platform (C)** is Google Cloud's managed hosting/runtime for an agent application we build, for example in ADK. Our Python agent code owns orchestration and calls Gemini models/tools. Google's runtime deploys and runs that application. The current product docs say build and deploy agents with ADK and separately identify the Gemini API custom managed-agent product.
3. **Interactions API (B)** is an API for model interactions and tool use. It can take native PDF inputs and use File Search, Google Search, and custom functions. It is not itself an ADK workflow engine or a persistent knowledge base.
4. There is also a **Managed Agents API on Agent Platform** (a second “managed agent” product). Its current Cloud docs describe a base Antigravity harness and mark the provisioning flow Preview. That is distinct from deploying an ADK application to Agent Runtime. The supported base-agent ID in that product is separately versioned from the Gemini Developer API saved-agent ID.

Thus “build a custom Gemini agent” can mean “save an Antigravity configuration” (A), or “write our own agent code” (C). Those mean different control, data-input, orchestration, and deployment boundaries. A's requirement to use Antigravity as its base agent does not apply to an ADK app deployed to Agent Runtime.

## Capability comparison

| Requirement | A. Saved Gemini API Custom Agent | B. Direct Interactions API + native PDF + File Search | C. Custom ADK app on Agent Runtime |
|---|---|---|---|
| **Native PDF** | Not supported by the Antigravity agent currently: its docs list only text and image, and explicitly say document input is unavailable. A saved agent cannot meet the required whole-chapter native PDF stage. | Supported. Interactions accepts `type: document` with PDF bytes or a Files API URI. Gemini processes native PDF text plus visual page content, including equations, diagrams, charts and tables. Document API limit is 50 MB or 1,000 pages; per PDF page counts as 258 tokens in the published accounting. | ADK is the app framework, not a separate PDF parser. It can call Gemini's native document understanding via the Gemini API / SDK as an ingestion step, then pass a validated source model to the other stages. |
| **Structured output** | The Antigravity-agent capability page says structured output is unsupported. Do not use it as the canonical edition generator. | Supported by Interactions `response_format` using JSON Schema subset, including when tools are used in documented examples. Validate and repair schema results in the application. | Available through the selected Gemini model's API calls. ADK can enforce typed inputs/outputs and app-side validation, but the runtime itself does not make model output correct. |
| **Multi-stage / subagents** | Agent can run steps in a task, but current limitations explicitly say no subagent delegation/nesting. | No application workflow engine implied by Interactions. The caller can sequence multiple requests, persist checkpoints and gate publication. | ADK has agent teams and graph workflows including sequential and parallel execution; suitable for ingestion → annotation → research → validation with a whole-edition publish barrier. |
| **Custom tools / MCP** | Supports custom function calling and remote MCP servers. The current Antigravity page calls out constraints (e.g. Streamable HTTP only for remote MCP); tool support is preview-bound. | Supports Function and MCP server tools, Google Search, URL Context, and File Search, subject to model/tool combination limits. Application executes custom functions. | ADK supports Python functions, toolsets, MCP integrations and service integrations; we own authentication, least privilege, approval boundaries and results. Agent Runtime can host the app and external tool connections. |
| **Saved skills / files** | This is A's strongest fit: save an agent and mount environment files such as `AGENTS.md`, `SKILL.md`, and workspace sources. Skills under `.agents/skills/` are auto-discovered by the Antigravity harness. They are instructions/resources in its environment, not a durable indexed personal knowledge base. | No saved agent/skills product required. Instructions and tool config are sent with each request; files uploaded to Files API last 48 hours. File Search gives persistent indexed documents. | Skills, prompts, and tool code are ordinary versioned app assets (and can use ADK's skills/tool interfaces). The deployed ADK app is our own code/config. Store user knowledge separately in a controlled database/object store or File Search. |
| **Persistent retrieval** | No supported File Search in the Antigravity harness per its official capabilities page; mounted files do not equal a searchable persistent knowledge store. | File Search stores chunked/embedded material indefinitely until deletion (while raw Files API objects expire after 48 hours). Search is semantic and returns source citations; retrieved tokens are billed normally. | ADK's `MemoryService` and `SessionService` separate long-term searchable memory from current session state; pick managed persistent implementations or our own store. Gemini Enterprise Agent Platform also documents Agent Search integrations. For exact source fidelity and portability, own canonical chapter blocks and provenance in app DB and use retrieval as an index. |
| **Google Search / Scholar-like work** | Antigravity defaults include `google_search` and `url_context`; can discover web sources but is not a structured literature database. | Google Search grounding returns web search evidence/citations; URL Context reads selected pages. This is not Scholar metadata/topology or verified intellectual relationships. | Add a Google search-grounding/web-research tool and a separate bibliographic provider/tool. ADK coordinates queries and evidence capture, but does not create academic coverage by itself. |
| **Sessions / state** | Interactions can continue using `previous_interaction_id`; background work requires storage enabled. This is interaction continuation, not the product's durable SQLite study state. | Interactions can store conversation history when `store=true` (default); set `store=false` if zero data retention is required. File Search remains persistent separately. Caller can instead persist controlled job state. | Agent Runtime supports agent sessions; for ADK, persistence requires implementing/using Agent Platform Sessions. ADK concepts distinguish session events/temporary state from long-term Memory. TTL is configurable in the session service; the documented VertexAiSessionService default is 365 days if unspecified. Keep durable study records under product lifecycle policy, not conversational memory. |
| **Deploy / preview** | Gemini API managed agents are in **preview**, schemas can change, and there is no versioning/rollback today. | Interactions API is documented as **preview** in the Antigravity capabilities page; direct model API use and model statuses vary. Native PDF and structured output are documented capabilities, but check chosen model/feature status at implementation time. | Agent Runtime is a Google Cloud managed deployment route; its docs describe it as fully managed and list ADK deployment. There is no single blanket GA label for every runtime capability in the overview. Cloud docs distinguish GA (`v1`) from Preview (`v1beta1`) by feature and region, and call A2A Preview. Verify the exact features/region needed before relying on them. Do not conflate a preview feature (A2A, etc.) with the entire ADK code path. |
| **Model options** | Only `antigravity-preview-09-2026` base; named agent options currently Gemini 3.8 Flash (default), 3.6 Flash, or 3.5 Flash-Lite. Named agent's model is fixed at creation. | Direct model choices depend on current Gemini API model/feature matrix; current docs include 3.8 Flash, 3.6 Flash, 3.5 Flash-Lite and additional models. Use the lowest model that meets the math fidelity bar and escalate selectively. | ADK is not tied to one model. Use Gemini models on Agent Platform initially; ADK can express multi-model orchestration and documents other provider support as well. |
| **Privacy / region** | Preview product, remote hosted harness and mounted files imply provider processing. The docs reviewed do not establish a specific regional processing control or product-level retention guarantee for A; verify terms before exposing private notes. | Gemini Developer API inputs should be treated under its own terms and retention behavior; Interactions stores state by default unless `store=false`. The separate Cloud zero-retention commitments for Agent Platform must not be assumed to apply automatically to a Developer API key. | Cloud offers stronger IAM, region/location and data processing controls. Google Cloud says it will not train models on customer data without permission/instruction, but zero retention is conditional: disable Interactions storage, request/response logging, and note Google Search grounding query/context logs may persist up to 3 days and cannot be disabled. Select a regional endpoint and verify each component's location; don't claim universal zero retention. |

### Boundaries and cautions

- Native PDF vision is important for a maths/physics edition. A text-only extraction may lose equation layout and diagrams, while native PDF supports visual plus textual interpretation. Native PDF is a model input capability, not a guarantee of exact transcription; store source page/block references and validate quotations, equations, and anchors against the original.
- File Search is valuable for recurring cross-chapter lookup; it is not the canonical source store. It chunks/indexes documents and uses semantic retrieval. Its raw source uploaded to the File Search import is deleted after 48 hours, while indexed embeddings remain until explicitly deleted. Keep the original PDF local and control the managed index's deletion/retention separately.
- File Search cannot be combined with Google Search or URL Context in the same request according to its limitations. Separate retrieval and external research into successive stages or use a custom app tool that explicitly performs both. Current docs list PDF as a File Search file type, but retrieval indexing is not the same capability as sending the entire chapter through native document understanding.
- Gemini API's free tier is described as data being used to improve Google's products, while paid tier says it is not. For private source work, don't assume free-tier use matches the product's privacy expectations.
- Google's Google Search grounding returns ordinary web results, not a Scholar API. Search-grounded claims and author-stated paper relationships must be distinguished from inferred links. Scholar-like structured citation topology remains an app/provider choice.
- For whole-chapter publishing, don't stream partial annotation into the reader as a completed edition. Persist internal stage outputs/checkpoints, validate all required blocks and citations, then atomically publish the complete edition.

## Per-chapter cost envelope (USD list-price calculation)

Assumptions: one 5–10 page PDF chapter, one native-PDF ingestion/generation run using Gemini 3.8 Flash Standard paid pricing effective through 2026-12-31; 20k–50k total billed input tokens after prompt/context plus 10k–30k billed output tokens including thinking; 5–10 Google Search queries; no cache discount; no retries; no external API spend. PDF pages contribute 258 image tokens each (1,290–2,580 tokens). Embedded native PDF text itself is not billed as tokens according to current document understanding notes, but image processing is counted. Thus the model-token range allows substantial prompt, source representation and complete annotated output beyond the page-image floor.

| Component | Low | High | Calculation |
|---|---:|---:|---|
| Gemini input | $0.015 | $0.0375 | 20k–50k × $0.75 / 1M tokens |
| Gemini output + thinking | $0.0375 | $0.1125 | 10k–30k × $3.75 / 1M tokens |
| Search grounding | $0.00 | $0.14 | First 5,000 requests/month shared across Gemini 3+ are free; otherwise up to 10 individual queries × $14/1,000 |
| **Estimated API total** | **$0.0525** | **$0.29** | Token cost + grounding; ignores search-free monthly quota in low estimate, includes no retries |

For a 5–10 page PDF, the bare PDF image-token component (1,290–2,580 input tokens) alone is about **$0.0010–$0.0019** at $0.75/M; overall chapter cost is driven much more by annotation output and repeated reasoning/context than by those page image tokens. These are a planning envelope, not a promised per-job cap: agentic loops and retries can increase usage. Put actual token/search-query usage in job records and enforce a per-job hard budget before enabling generation.

Agent Runtime adds infra charges: current list price is $0.085 per allocated vCPU-hour and $0.009 per allocated GiB-hour, rounded to seconds, and Runtime idle waiting between prompts is not billed. At a deliberately simple 1 vCPU + 1 GiB for one active hour, this is about **$0.094 per active runtime hour**, plus model calls and any storage, search, data transfer or other service charges. Session storage is $0.30/GiB-month; operation charges are $0.085 per 1M writes and per 3M reads (as stated on the current pricing page). Actual Agent Runtime resource allocation and deployment costs must be measured in the chosen region; no Cloud Runtime amount is included in the API envelope above.

The published Gemini 3.8 Flash Standard price rises to $1.50/M input and $7.50/M output from 2027-01-01, doubling the token component (about $0.105–$0.30 here before search/runtime) from today's pre-2027 price. This is an announced schedule on the pricing page, so reevaluate budgets before 2027.
